# workflow.md — 作業の進め方（トークン節約のためのモデル分担）

このプロジェクトは個人開発で、消費トークンがそのままコストになる。
**判断の要る作業とタイプ量の多い作業を分離し、後者を安いモデルに落とす**のが基本方針。

---

## 1. 役割分担

| 作業 | モデル | 理由 |
|---|---|---|
| 仕様の解釈、境界条件の確定、型設計、レビュー | **Opus** | ここを間違えると下流が全部やり直しになる |
| 確定済み契約どおりの実装、テスト記述、雛形生成、設定ファイル | **Sonnet**（サブエージェント） | 判断が不要。契約書があれば書けるだけ |
| 誤字修正、リネーム、フォーマット | Sonnet または手作業 | Opus を起動する価値がない |

**レンジデータの入力は人間のみ**（`CLAUDE.md` §2.1）。どのモデルにも投げない。

---

## 2. なぜ「設計を先に文書化する」とトークンが減るのか

サブエージェントは毎回**文脈ゼロ**で起動する。指示が曖昧だと、エージェントはリポジトリを
探索して仕様を推測しようとし、その探索が丸ごとトークンになる。さらに推測が外れれば
やり直しで二重に払う。

したがって `docs/domain-contracts.md` は「設計書」であると同時に**サブエージェントへの入力**である。
シグネチャ・境界条件・テストケースまで書いてあれば、エージェントは
「そのファイルだけ読んで、指定ファイルだけ書く」で完結する。

### 依頼テンプレート

```
参照するファイルは docs/domain-contracts.md の §N のみ。他は読まない。
書くファイル：src/domain/xxx.ts と tests/xxx.test.ts の 2 つだけ。
§N のシグネチャと境界条件をそのまま実装する。仕様を自分で判断しない。
曖昧な点があれば実装せず、質問を報告して終了する。
完了条件：npx vitest run tests/xxx.test.ts が通る。
```

- 参照範囲を明示する（読ませない範囲を決めるのが効く）
- 書いてよいファイルを列挙する（隣接ファイルの「ついでの改善」を止める）
- **迷ったら実装せず質問させる。** 勝手な判断を後から直すのが一番高くつく
- 完了条件をコマンドで書く（「動くはず」で終わらせない）

---

## 3. 並列化の指針

依存の無いタスクは同時に走らせる。ただし**同じファイルを触るタスクは並列にしない**
（`package.json` の取り合いが典型）。

```
1. 足場（package.json / vite / tailwind / vitest / CI）      ← 単独で先に
2. domain 4 モジュール、storage、validate スクリプト        ← 並列可
3. UI                                                        ← domain 完了後
```

---

## 4. Opus を使うべきタイミング（節約しすぎない）

以下は安いモデルに落とすと結局高くつく。

- `CLAUDE.md` / `plan.md` の変更を伴う判断
- 採点・サンプリングの**仕様そのもの**の変更（境界条件は学習効果に直結する）
- テストが落ちた原因が「実装のバグ」か「仕様の穴」か切り分ける作業
- v0.2 以降の着手判断（`plan.md` の「判断ポイント」）

---

## 5. セッションを跨ぐときの節約

- 会話を続けるより、**`plan.md` のチェックボックスを更新して次のセッションを新規に始める**方が安い。
  長い会話の文脈を毎ターン読み直すコストは、`CLAUDE.md` + `plan.md` を読み直すコストより高くなる。
- 常設で読ませるのは `CLAUDE.md` と `plan.md` だけに保つ。詳細は `docs/` に置き、必要なときだけ開く。
  だから `CLAUDE.md` に実装の細部を書き足さない。

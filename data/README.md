# data/ranges — レンジデータ入力手順

## 大前提

**このディレクトリの数値は人間しか入力しない。** Claude は推測・生成・補完してはならない
（`CLAUDE.md` §2.1）。欠けているハンドを見つけても埋めない。バリデータが警告を出す。

わずかにズレたレンジを数千回反復するのは、何もしないより悪い。誤ったものを高速で自動化してしまう。

---

## 手順

1. 出典ツールでチャートを開く（フォーマット・レート・スタックを確認する）
2. `6max_100bb_rfi_<position>.json` を作る。ファイル名の `<position>` は小文字
3. `id` はファイル名（拡張子なし）と一致させる
4. `source` を**先に**埋める。空のままハンドを入力し始めない
5. `ranges` を入力する
6. `npm run validate` を通す

## ファイル形式

```json
{
  "schema_version": 1,
  "id": "6max_100bb_rfi_btn",
  "format": "6max",
  "stack_bb": 100,
  "spot": "RFI",
  "hero_position": "BTN",
  "villain_position": null,
  "actions": ["raise", "fold"],
  "source": {
    "name": "<ツール名 / フォーマット / レート>",
    "url": "<URL>",
    "retrieved_at": "2026-08-15",
    "entered_by": "juno",
    "notes": "<オープンサイズ、アンティ有無、ICM の有無など>"
  },
  "ranges": {
    "AA": { "raise": 1.0, "fold": 0.0 },
    "K9o": { "raise": 0.32, "fold": 0.68 }
  }
}
```

### 表記規則（`CLAUDE.md` §5）

- ランクは `A K Q J T 9 8 7 6 5 4 3 2`。`10` ではなく `T`
- 高いランクを先に：`AKs`。`KAs` はバリデータが**エラーにする**（自動で並べ替えない）
- ペアはサフィックスなし（`AA`）、スーテッドは `s`、オフスートは `o`
- 各ハンドの頻度合計は `1.0 ± 0.01`
- 記載の無いハンドは `fold: 1.0` として扱われる。全 169 を書く必要はないが、
  **意図的な省略か入力漏れかは区別できない**ので、`source.notes` に「フォールドは省略」と書く

### アクション名の規約

**レイズサイズをアクション名に入れない。** `raise_2.5` ではなく `raise` と書く。

1 つのチャートに現れるレイズサイズは 1 つだけなので、サイズは「どうするか」の答えに情報を足さない。
サイズは `source.name` と `source.notes` に記録する。こうしておくと、キーボードショートカット（`R`）、
チャート横断の統計、アクションボタンの実装がそのまま使える。

複数サイズが混在するチャートを入れたくなったら、それはスキーマの変更を伴う設計判断なので、
先に `CLAUDE.md` を直す。

**SB のリンプは `call` ではなく `limp`。** v0.3 で入る「レイズに対するコール」と同じ名前にすると、
アクション別の集計が混ざって意味を失う。

### 入力を省略してよい場合

RFI のように「レイズしない = フォールド」が明らかなスポットでは、レイズ頻度が 0 より大きい
ハンドだけを書けばよい。バリデータは欠損件数を警告として出すが、ビルドは通る。

## 検算手順（スクリーンショットから抽出した場合は必須）

`npm run validate` を通すだけでは足りない。**合計が合っていてもセル単位の誤りは検出できない。**
値が入れ替わる種類の誤りは合計を変えないので、コンボ数の照合を素通りする。

1. `npm run validate` を実行し、**`suspicious-monotonicity` の警告がゼロ**であることを確認する。
   ここに出るのは「強いハンドより弱いハンドの方が多くプレイされている」組で、ほぼ確実に転記ミス。
2. コンボ数をツールの表示と照合する。**ただしこれは必要条件であって十分条件ではない**（上記の理由）。
3. 抜き取りで 10 ハンド、ツールの画面と目視で突き合わせる。混合頻度のハンドを優先して選ぶ
   （純粋なハンドは誤っていても気づきにくい）。

### 検算そのものを間違えた例（2026-08-15）

GTO Wizard のスクリーンショットからピクセル計測で抽出した 5 チャートに対し、当初
「強いハンドより弱いハンドが多くプレイされている」組を 9 件検出し、抽出バグと判断しかけた。

**が、その判定規則の方が誤りだった。** `96s > 86s`（上のカードが高い方が強い）と
`A6o > A5o`（キッカーが高い方が強い）を支配関係として使っていたが、前者はギャップの広さを、
後者はホイールストレートを無視している。どちらもソルバーの正常な出力を「誤り」と呼んでいた。

健全な 3 規則（`docs/domain-contracts.md` §5）に絞ると、違反は BTN 0 件 / SB 0 件 /
UTG・HJ・CO 各 2 件（いずれもレイズ頻度 0.25 以下で、出題の正解は変わらない）まで減った。
スクリーンショットとの目視照合 12 セルもすべて一致した。データは破棄せず採用した。

教訓は 2 つ：

1. 合計の一致は「正しさ」ではなく「スケールが合っていること」しか意味しない
2. **チェック規則そのものを疑う。** ポーカーの直感で作った「強さの順序」は、
   ギャップやホイールのような効果を落としやすい。警告が出たら、まず規則の側を検算する

### ICM の扱い（v0.4 で重要）

プッシュ/フォールド表を入れるときは、**ICM 補正入りかチップ EV ベースかを `source.notes` に必ず書く。**
両者を混ぜて反復すると学習が壊れる（`plan.md` v0.4）。

## テスト用フィクスチャについて

`tests/fixtures/` に置いてあるチャートは**合成値で、実戦の学習には使えない**。
バリデータと採点ロジックの検証専用。`data/ranges/` にコピーしないこと。
